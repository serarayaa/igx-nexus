# IGX NEXUS — Scope Freeze: Road to 1.0 IT CMDB

Estado: **APPROVED**  
Ticket: **V03-CMDB-00**

## Product statement

La primera versión mayor de NEXUS será **NEXUS 1.0 — IT CMDB & Asset Management**.

GLPI continúa como System of Record de CMDB/ITAM. GLPI Agent entrega inventario automático. NEXUS agrega modelo canónico, provenance, reconciliación, snapshots, historial semántico, calidad, workflows operativos y una experiencia moderna de producto.

La meta no es una demo de CMDB: **1.0 debe poder operar de verdad**.

## Release philosophy

No se inicia NEXUS 2.0 mientras el alcance definido para 1.0 no esté completo, probado y operando de forma estable.

Las versiones menores `1.1`, `1.2`, etc. pueden seguir perfeccionando IT CMDB sin forzar un salto prematuro a OT.

## Exit gate 1.0

> Puedo descubrir o registrar un equipo, encontrarlo, abrirlo, entender qué es, dónde está, quién lo usa, qué hardware/software tiene, cuál es su estado, cuándo fue observado, qué cambió, qué tan completa es su información y ejecutar sus workflows normales de entrega/devolución con documentación trazable.

## Alcance obligatorio

### Inventory & Discovery

- computers, notebooks, desktops y servers;
- monitors, printers, peripherals y network equipment;
- software, versiones e instalaciones;
- operating system;
- manufacturer/model/type;
- serial, asset tag y otros identificadores observados;
- inventory freshness y source provenance.

### CMDB operacional

- entity y location;
- user/owner/technician cuando la fuente lo soporte;
- lifecycle/status;
- relationships;
- Asset 360;
- búsqueda;
- calidad del inventario;
- changes/history.

### Asset Management

- alta/registro;
- preparación;
- asignación;
- cambio de usuario o ubicación;
- reparación;
- reemplazo;
- devolución;
- stock/reasignación;
- baja/retiro.

### Documentos operativos

NEXUS 1.0 debe poder generar o preparar documentos trazables para workflows reales, por ejemplo:

- acta de entrega;
- acta de devolución;
- comprobante de cambio/reemplazo;
- ficha del activo;
- inventario por usuario o ubicación;
- etiquetas/QR;
- exportaciones PDF/Excel cuando correspondan.

Debe organizar información por intención:

- Identity
- Assignment
- Hardware
- Operating System
- Storage
- Software
- Network
- Lifecycle
- Relationships
- History
- Provenance / Sources

No debe ser un formulario GLPI maquillado ni una lista indiscriminada de campos.

## Core architecture

### Core obligatorio

`GLPI + GLPI Agent + NEXUS` deben bastar para que 1.0 funcione.

Ninguna integración opcional puede bloquear la release.

### Integraciones opcionales

#### Entra ID

Evaluar para identidad/account/org cuando aporte datos exclusivos o más confiables.

#### Intune

Evaluar para endpoint management, enrollment, compliance, primary user y otros datos de administración que GLPI no entregue.

#### Google Workspace

Evaluar sólo si aporta información útil y no duplica innecesariamente GLPI/Entra.

#### Zabbix

Fuente de telemetría operacional cuando ya exista en el entorno. NEXUS no debe recrear un sistema de monitoring.

### Authority / provenance

Cada dato mantiene fuente y autoridad explícitas. Una integración nueva no reemplaza silenciosamente a otra.

## Endpoint Health — opcional

No es requisito de NEXUS 1.0.

Puede incorporarse como stretch goal de 1.0 o en 1.x si es estable y mantenible.

Objetivo:

> identificar señales observables de que un endpoint puede requerir atención.

Señales candidatas:

- battery health;
- storage SMART / NVMe health;
- media errors / wear;
- Windows Event Log relevante;
- unexpected restarts;
- hardware/storage errors;
- sensores/temperatura cuando sean confiables.

Orden de evaluación:

1. GLPI Agent;
2. smartmontools para disco/storage;
3. Zabbix para telemetría operacional;
4. collector Windows acotado si hace falta;
5. herramientas de cybersecurity sólo cuando su dominio lo justifique.

NEXUS debe consumir estados o findings semánticos con provenance, no acumular necesariamente toda la telemetría cruda.

## Changes / History

GLPI aporta estado actual y evidencia auxiliar donde corresponda.

NEXUS conserva snapshots normalizados y produce diffs semánticos para cambios de owner, location, software, lifecycle/status, hardware, relaciones e inventory freshness.

No atribuir actor o causalidad si la fuente no lo demuestra.

## Seguridad

- service identity dedicada;
- least privilege;
- deny-by-default;
- no direct DB writes;
- no secretos en Git;
- no elevación a Admin/Super-Admin para resolver 403;
- browser nunca consulta GLPI directamente.

## Accesibilidad

Gate transversal: teclado completo, foco visible, contraste objetivo WCAG AA, screen-reader semantics, reduced motion, estados no dependientes sólo de color, alternativa semántica para charts/graphs y reflow móvil razonable.

## Dirección visual

La experiencia debe ser corporativa premium, moderna y data-dense sin caer en card soup, neon/cyberpunk, movimiento permanente ni admin templates genéricos.

La dirección final se valida después de estabilizar el contrato CMDB/backend suficiente para evitar retrabajo.
